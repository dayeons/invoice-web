# Task 009: 캐시 전략, 성능, 접근성 개선

## 개요
Task 008까지 기능은 완성되었습니다. 이 작업은 측정값을 근거로 (1) 캐시 수명과 PDF 캐싱 여부를 결정하고, (2) 필요하면 즉시 반영 수단(재검증 Route Handler)을 두고, (3) Lighthouse 모바일 성능 90점 이상, 접근성 95점 이상을 확인하고 실제로 모자란 부분만 고치고, (4) 한글 폰트 서브셋 여부를 결정합니다. **결정과 수정은 아래 "기준 측정값"을 근거로만** 합니다. 이 단계(T12)에서는 코드를 바꾸지 않고 작업 파일과 기준값만 만듭니다.

작업은 다음 단계로 나뉩니다.
- T12: 작업 파일 작성과 변경 전 기준 측정 (이 문서의 "기준 측정값")
- T13: 캐시 수명과 PDF 캐싱 결정 기록
- T14: 재검증 Route Handler 구현과 검증 (**사용자에게 도입 여부 확인 후**)
- T15: 접근성과 Lighthouse 개선
- T16: 폰트 서브셋 검토와 적용 여부 결정
- T17: Task 008 전체 여정과 Task 004 반응형 회귀, ROADMAP 반영

### 결정에 필요한 사실 (설치된 Next.js 16.4.6 문서 기준)
- `cacheLife("minutes")`: `stale` 5분(클라이언트가 서버 확인 없이 쓰는 시간), `revalidate` 1분, `expire` 1시간. (`cacheLife.md`)
- `revalidateTag(tag, profile)`는 Server Function과 Route Handler에서 호출합니다. 두 번째 인자가 없는 형태는 deprecated이며 `{ expire: 0 }`와 같습니다. `"max"`는 stale-while-revalidate(오래된 값을 먼저 주고 뒤에서 갱신), `{ expire: 0 }`는 다음 요청이 바로 새로 가져옵니다. 외부 웹훅이나 다른 서비스가 Route Handler로 부르는 경우 문서는 `revalidateTag(tag, { expire: 0 })`를 안내합니다. (`revalidateTag.md`)
- `updateTag`는 Server Action 안에서만 쓸 수 있어 Route Handler에는 쓸 수 없습니다. (`updateTag.md`)
- 재검증은 호출 시점이 아니라 **다음 요청 때** 일어납니다. (`revalidateTag.md`)
- Task 008에서 관찰: 운영 모드에서 `revalidate` 경과 후 첫 요청부터 새 값이 나왔고, 화면과 PDF가 `getInvoice` 캐시를 공유합니다(tasks/008 T11).
- `invoiceCacheTag(pageId)` 형식은 `invoice-<하이픈 없는 소문자 32자리>`이며 `getInvoice`의 `cacheTag`와 재검증 코드가 같은 함수를 써야 합니다. (shrimp-rules 4.1)

## 결정 기록

### T13: 캐시 수명과 PDF 캐싱 (2026-11-20)
**결정 1: `getInvoice`의 `cacheLife("minutes")`를 유지한다 (코드 변경 없음).** 서버 재검증 1분, 클라이언트 stale 5분, 만료 1시간.
- 근거(노션 호출 수): 캐시 없는 첫 조회는 페이지 1회 + 항목 N회(3개씩 묶음) 정도입니다(항목이 25개 이상이면 관계 속성 조회 1회 추가). 항목 3개는 약 4회, 25개는 약 27회, 30개는 약 32회입니다. 실측 첫 조회는 3개 0.68s, 25개 3.69s, 30개 3.34s였고 429와 재시도는 0건이었습니다. 재검증 주기가 1분이면 한 견적서가 계속 열려 있을 때 호출은 최대 분당 약 32회(평균 초당 0.5회 미만)입니다. 노션의 평균 초당 3회 제한에 대해 항목 30개짜리 견적서 약 6개가 동시에 계속 열려 있어야 걸리므로 MVP 규모에서는 여유가 있습니다.
- 근거(실시간성): PRD의 "실시간 조회"에 대해 Task 008에서 노션 값 수정 후 약 1분 안에 화면과 PDF에 반영됨을 확인했습니다. 수정 직후 1분 이내에는 이전 값이 보일 수 있습니다.
- 대안과 보류 사유
  - `revalidate`를 늘림(예: 5분): 호출 수는 줄지만 갱신이 더 늦어져 "실시간" 기대와 멀어짐. 호출 수에 여유가 있어 이득이 작음.
  - `revalidate`를 줄임(예: 10~30초): 갱신은 빨라지지만 호출이 늘고 `cacheLife`의 짧은 값은 프리렌더에서 제외되는 규칙(`revalidate` 0 또는 `expire` 5분 미만은 동적 구멍)과 부딪힐 수 있음. 지금은 이득 대비 이유가 부족함.
  - 즉시 반영이 필요하면 캐시 수명을 줄이지 않고 T14의 재검증 Route Handler로 해결(도입 여부는 사용자 결정 대기).
- 이 결정은 사용자가 실시간성 기대치를 더 높게 요구하면 바꿀 수 있습니다(`src/lib/notion/invoice.ts`의 `cacheLife` 한 줄과 ROADMAP 기술 결정 표의 "실시간성과 캐시" 행). 사용자 의견이 없어 기본안을 유지했습니다.

**결정 2: PDF 결과 캐싱은 도입하지 않는다 (코드 변경 없음).** `Cache-Control: private, no-store` 유지.
- 근거: T12 측정에서 PDF 렌더링은 항목 0개 0.03s, 25~30개 약 0.07~0.08s, 파일 크기 약 70KB입니다. 노션 조회가 필요한 경우(캐시 미스)에도 시간은 노션 조회가 지배하고 그 부분은 `getInvoice` 캐시가 이미 해결합니다. 같은 견적서를 반복 다운로드해도 비용이 낮아 별도 PDF 캐시의 이득이 거의 없습니다.
- 도입 시 비용: PDF를 캐시하면 `getInvoice`와 같은 태그(`invoiceCacheTag`)로 무효화해야 하고, 그렇지 않으면 화면과 PDF 값이 어긋날 수 있습니다. 무효화 경로를 하나로 유지하는 쪽이 단순하고 안전합니다.
- 대안: `"use cache"`로 PDF 바이트를 캐시하고 같은 태그를 붙임. 렌더링 시간이 눈에 띄게 늘거나(예: 항목 수백 개) 서버리스 실행 시간 비용이 문제가 되면 재검토.

### T14: 재검증 Route Handler 도입 (2026-11-20)
**결정: 도입한다.** 사용자가 T14~T18 실행을 요청하며 도입을 승인했습니다. 캐시 수명(`cacheLife`)은 바꾸지 않고, 즉시 반영이 필요할 때만 이 엔드포인트를 씁니다.
- 위치와 계약: `src/app/api/revalidate/route.ts`, `POST` 전용. 헤더 `Authorization: Bearer <REVALIDATE_SECRET>`, 본문 `{"id": "<노션 페이지 ID>"}`. 응답은 모두 `Cache-Control: no-store`.
- 응답 코드: 성공 200 `{"revalidated":true}`, 토큰 없음/불일치 401, 형식 오류 ID/본문 없음/JSON 아님 400, 다른 메서드 405(Next가 자동 응답), `REVALIDATE_SECRET` 미설정 503(어떤 요청도 받지 않음).
- 구현: `crypto.timingSafeEqual`(길이가 다르면 사전 거부), `isNotionId`로 형식 검사(노션 미호출), `revalidateTag(invoiceCacheTag(id), { expire: 0 })`(Route Handler에서는 `updateTag` 불가, `revalidateTag.md` 기준). 존재하지 않는 ID도 태그만 만료시키므로 200으로 응답합니다(무해, 존재 여부를 알려 주지 않음).
- 환경변수 `REVALIDATE_SECRET`(서버 전용): `.env.example`에 자리표시자 추가. Vercel 등록은 Task 010.

### T16: 폰트 서브셋 (2026-11-20)
**결정: 보류한다 (코드와 폰트 파일 변경 없음).**
- 측정(운영 빌드, 서버 재시작 직후 견적서를 먼저 조회해 노션 캐시를 데운 뒤 PDF 요청, 항목 3개): 첫 PDF 0.189s, 이어서 0.029s, 0.024s, 0.023s. 서버 인스턴스당 첫 PDF에만 폰트 로딩으로 약 0.16s가 더 듭니다(`registerPdfFonts`는 프로세스당 한 번만 등록). 서버 프로세스 RSS 약 276MB.
- 서브셋으로 줄어드는 것은 이 첫 요청의 약 0.16s와 함수 번들(폰트 파일 합계 약 9.5MB: Regular 4,644,748B, Bold 4,816,044B)뿐입니다. PDF 파일 크기는 react-pdf가 쓰인 글리프만 임베드하므로 이미 약 68.5KB이고 서브셋과 무관합니다. 노션 첫 조회(항목 3개 약 0.7s~2.4s, 30개 약 3.3s)에 비하면 작은 값입니다.
- 위험: 견적서 내용은 사전에 정해지지 않은 사용자 텍스트라 서브셋에서 빠진 글자가 두부 문자(□)로 나올 수 있습니다. 완성형 한글 11,172자와 라틴, 숫자, 기호를 모두 넣으면 크기 이득도 크게 줄어듭니다. 또 서브셋 도구를 새로 도입하고 폰트 파일을 갱신하는 유지 부담이 생깁니다.
- 아직 모르는 것: Vercel 함수에 폰트 파일이 포함되는지와 번들 크기가 한도 안인지는 로컬에서 확인할 수 없습니다. 배포 검증(T19)에서 확인하고, 한도 문제나 콜드 스타트가 실제로 문제로 나타나면 그때 서브셋을 다시 검토합니다(`src/lib/pdf/fonts.ts`의 등록 경로만 바꾸면 되는 구조이며 `OFL.txt`는 유지).
