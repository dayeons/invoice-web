# 노션 견적서 뷰어 개발 로드맵

노션에 작성한 견적서를 클라이언트가 가입 없이 고유 링크로 웹에서 확인하고 PDF로 내려받게 하는 MVP입니다.

## 개요

노션 견적서 뷰어는 견적서를 발행하는 프리랜서와 소규모 기업, 그리고 견적서를 받는 클라이언트를 위한 서비스입니다. 관리 화면을 따로 두지 않고 노션을 그대로 견적서 저장소로 씁니다. 제공 기능은 다음과 같습니다.

- **노션 데이터베이스 연동 (F001)**: Notion API로 견적서와 견적 항목 데이터를 서버에서 조회
- **견적서 조회 (F002)**: `/invoice/[notionPageId]` 고유 URL로 발행일, 유효기간, 항목별 금액, 총액 표시
- **PDF 다운로드 (F003)**: 버튼 한 번으로 견적서를 PDF로 생성하고 다운로드
- **견적서 URL 생성 (F010)**: 노션 페이지 ID로 공유 링크를 만들어 노션 안에서 바로 복사
- **유효성 검증 (F011)**: 없거나 접근할 수 없는 견적서 ID는 404 안내 페이지로 처리
- **반응형 레이아웃 (F012)**: 모바일, 태블릿, 데스크톱에서 모두 읽기 좋은 화면

## 개발 워크플로우

1. **작업 계획**

- 기존 코드베이스를 학습하고 현재 상태를 파악
- 새로운 작업을 포함하도록 `docs/ROADMAP.md` 업데이트
- 우선순위 작업은 마지막 완료된 작업 다음에 삽입

2. **작업 생성**

- 기존 코드베이스를 학습하고 현재 상태를 파악
- `/tasks` 디렉토리에 새 작업 파일 생성 (디렉토리가 아직 없으므로 처음에 `tasks/000-sample.md` 템플릿과 함께 생성)
- 명명 형식: `XXX-description.md` (예: `003-invoice-components.md`)
- 고수준 명세서, 관련 파일, 수락 기준, 구현 단계 포함
- **API/비즈니스 로직 작업 시 "## 테스트 체크리스트" 섹션 필수 포함 (Playwright MCP 테스트 시나리오 작성)**. UI 작업도 렌더링과 반응형 확인용 "## 테스트 체크리스트"를 둠
- 테스트 체크리스트는 다음 네 묶음으로 나누고, 시나리오마다 기대 결과를 함께 적음 (예: "`/invoice/abc` 접속 → '견적서를 찾을 수 없습니다' 표시, 응답 상태 404")
  - 정상 케이스: 유효한 데이터 조회와 표시, 주요 버튼 동작
  - 에러/예외 케이스: 존재하지 않는 ID, 외부 API(노션) 실패, 환경변수/권한 오류
  - 경계값/엣지 케이스: 빈 데이터, 항목 0개/다수, 매우 긴 값, 특수문자, 잘못된 형식 입력
  - 반응형: 모바일(375px), 태블릿(768px), 데스크톱(1280px)에서의 표시와 동작
- 작업 파일 끝에 "## 테스트 결과" 섹션을 비워 두고, 구현 단계에서 채움
- 마지막으로 완료된 작업 파일 1~2개를 예시로 참조. 예를 들어 현재 작업이 `006`이면 `005`와 `004`를 참조
- 완료된 작업 파일에는 체크된 박스와 변경 사항 요약이 있음. 새 작업 파일에는 빈 체크박스만 두고 변경 사항 요약은 비워 둠. 초기 상태 샘플은 `000-sample.md` 참조

3. **작업 구현**

- 작업 파일의 명세서를 따름
- Next.js 관련 코드는 작성 전에 `node_modules/next/dist/docs/`의 해당 가이드를 먼저 확인 (설치 버전이 학습 데이터와 다를 수 있음)
- **구현을 한 후에는 반드시 테스트를 수행해야 함 (예외 없음)**
- **API 연동 및 비즈니스 로직 구현 시 Playwright MCP로 꼼꼼하게 테스트 수행 필수**
- 각 단계 후 작업 파일 내 단계 진행 상황 업데이트
- 단계마다 `npm run lint`, `npx tsc --noEmit` 통과 확인, 작업 완료 시 `npm run build` 통과 확인
- 구현 완료 후 `npm run dev` 서버를 띄우고 Playwright MCP로 E2E 테스트 실행 (테스트 체크리스트의 모든 시나리오 수행)
- 테스트 실패 시 원인을 수정하고 재테스트함. 모든 테스트 통과를 확인한 후에만 다음 단계로 진행
- 테스트 수행 결과(시나리오별 통과/실패, 실패 원인과 수정 내용, 재테스트 결과)를 작업 파일의 "## 테스트 결과" 섹션에 기록
- 각 단계 완료 후 중단하고 추가 지시를 기다림

4. **로드맵 업데이트**

- 테스트 체크리스트 전 항목 통과가 작업 파일에 기록된 Task만 로드맵에서 ✅로 표시하고 `See: /tasks/XXX-xxx.md` 참조 추가
- 테스트를 하지 않았거나 실패 항목이 남은 Task는 코드가 다 작성되었더라도 ✅로 표시하지 않음

## 테스트 원칙

모든 구현 Task에 공통으로 적용합니다.

1. **구현 후 테스트 필수**: 모든 구현 Task는 구현 직후 테스트 단계를 거칩니다. 테스트 체크리스트 전 항목이 통과해야 완료(✅)로 처리할 수 있습니다.
2. **Playwright MCP 사용**: 브라우저 기반 E2E와 통합 테스트는 모두 Playwright MCP로 수행합니다. 화면 폭 변경(375/768/1280px), 접근성 스냅샷, 콘솔 메시지, 네트워크 요청, 다운로드 이벤트를 Playwright MCP로 확인합니다. 테스트 러너가 없으므로 `lint`, `tsc --noEmit`, `build`는 보조 검증이며 테스트를 대신하지 않습니다.
3. **API 연동과 비즈니스 로직 Task는 상세하게**: 다음 네 가지를 모두 시나리오로 작성하고 기대 결과를 적습니다.
   - 정상 흐름: 유효한 견적서 조회와 표시, PDF 다운로드
   - 에러 처리: 존재하지 않는 ID, 노션 API 실패, 잘못된 API 키나 누락된 환경변수
   - 엣지 케이스: 빈 필드, 항목 0개와 25개 이상, 매우 긴 항목명, 특수문자, 큰 금액, 잘못된 ID 형식
   - 데이터 정합성: 화면과 PDF에 표시된 값이 노션 원본 값과 일치하는지
4. **각 Task에 테스트 항목 명시**: 로드맵의 각 Task 마지막에 "테스트 체크리스트 (Playwright MCP)"를 두고 검증할 시나리오를 요약합니다. 상세 시나리오는 작업 파일의 "## 테스트 체크리스트"에 적습니다.
5. **단계별 검증**: 큰 Task(예: Task 004, 005, 006)는 하위 단계마다 해당 범위의 시나리오를 먼저 테스트해서 문제를 일찍 찾습니다.

### 상태 표시 규칙

- **Phase 제목 + ✅**: 속한 Task가 모두 완료된 Phase
- **Task ✅ - 완료**: 테스트 체크리스트 전 항목 통과가 작업 파일에 기록된 Task. `See: /tasks/XXX-xxx.md` 참조를 함께 적음
- **Task - 우선순위**: 바로 시작할 Task
- **Task 상태 없음**: 대기 중인 Task
- **세부 구현 사항 ✅**: 코드 작성이 끝난 항목. 세부 항목이 모두 ✅여도 테스트를 통과하기 전에는 Task를 완료로 표시하지 않음

## 의존성과 병렬 작업

```
Task 001, 002 (완료)
   ├── Task 003 → Task 004 ──────────────┐   UI 흐름 (더미 데이터)
   └── Task 005 (노션 실데이터 검증) ──────┼── Task 006 (PDF) → Task 008 (통합 테스트) → Task 009 → Task 010
       Task 007 (공유 URL, 독립 진행 가능) ┘
```

- Task 003~004(UI)와 Task 005(노션 실데이터 검증)는 `Invoice` 타입만 공유하므로 동시에 진행할 수 있습니다.
- Task 006의 PDF 문서 컴포넌트는 Task 003의 정보 구조를 따르므로 Task 003 이후 시작합니다. Route Handler는 Task 005의 `getInvoice`를 그대로 씁니다.
- Task 007은 다른 작업과 의존성이 거의 없어 언제든 끼워 넣을 수 있습니다.

## 기술 결정 사항과 위험 요소

| 항목 | 내용 | 대응 |
| --- | --- | --- |
| PDF 한글 깨짐 | `@react-pdf/renderer` 기본 폰트에는 한글 글리프가 없음 | Task 006에서 한글 폰트 등록을 필수 단계로 둠 |
| PDF 요청 위조 | PRD 예시처럼 클라이언트가 견적서 데이터를 POST하면 내용을 조작한 PDF를 만들 수 있음 | ID만 받는 GET Route Handler에서 서버가 다시 조회 |
| 링크 추측 노출 | Integration에 공유된 다른 노션 페이지가 ID만으로 노출될 수 있음 | `belongsToInvoiceDatabase` 검사(구현됨) 유지, `noindex` 적용(구현됨) |
| 노션 속도 제한 | 평균 초당 3회 제한. 항목이 많으면 병렬 조회가 제한에 걸릴 수 있음. SDK의 자동 재시도(기본 2회)가 실패를 가려 지연으로만 나타남 | 캐시(구현됨)와 3개씩 묶음 조회(코드 작성됨), 재시도 로그로 확인(Task 005) |
| 실시간성과 캐시 | PRD는 "실시간 조회"를 요구하지만 현재 서버 1분 재검증(클라이언트 stale 5분, 만료 1시간) | Task 009에서 캐시 수명과 즉시 재검증 방식 결정 |
| Cache Components 제약 | 서버 컴포넌트에서 `new Date()`, `Math.random()`을 바로 쓰면 빌드 실패 | 비결정 값은 `"use cache"` 또는 `<Suspense>` 경계 안에서만 사용 |
| Base UI 기반 shadcn | Radix의 `asChild`가 없음 | `render` prop, 링크 버튼은 `buttonVariants()` 사용 |
| PRD와 실제 버전 차이 | PRD는 Next.js 15.5.3, 실제는 16.4.6 | 구현 전 `node_modules/next/dist/docs/` 확인 |

## 범위 밖 (MVP 이후)

아래 기능은 이번 로드맵에 넣지 않습니다. MVP 출시 후 사용자 피드백을 보고 별도 로드맵으로 계획합니다.

- **관리 기능**: 관리자 대시보드(발행한 견적서 목록, 통계), 견적서 상태 관리(승인/거절/대기 추적), 검색과 필터링
- **자동화**: 이메일 자동 발송(SendGrid/Resend 연동), 견적서 만료일 설정과 만료 알림, 클라이언트 응답 트래킹
- **고급 기능**: 견적서 템플릿 커스터마이징과 다중 템플릿, 다국어 견적서, 전자 서명, 견적서 버전 관리와 히스토리
- **인증**: 로그인, 회원가입, 권한 관리 (MVP는 고유 링크 공개 접근만 지원)

참고: 노션 DB의 `상태` 값은 MVP에서 화면에 배지로 표시만 하고, 상태 변경이나 상태별 접근 제어는 하지 않습니다.
